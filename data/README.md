# Data

All data in this repository is synthetic. Company, plant, material,
supplier, vessel, and forwarder names are fictional. Relationships between
fields are designed to be plausible, but they are not real statistics.

| Folder | In Git | Purpose |
|---|---|---|
| `seed/` | Yes | Starting state for every demo run and test. Generated by `scripts/generate_seed.py`; do not edit by hand (`tests/test_seed.py` fails if it drifts from the generators). |
| `runtime/` | No | Working copy that the tools read and write during a run. Replaced on every reset. |

Reset before each demo run:

```
python scripts/reset_data.py
```

## What is in `seed/`

| Path | Content | Shape |
|---|---|---|
| `s4/<service>/<entity set>.json` | Purchase orders (and STOs), stock, safety stock, suppliers | Mock S/4HANA |
| `logistics/shipments.json` | Shipments: status, port, ETA, exception, events | Simulated logistics event feed |
| `logistics/event_catalog.json` | Prepared events for the demo's event feed | Simulated logistics event feed |
| `documents/<shipment>/*.txt` | Invoice, packing list, bill of lading, certificate of analysis | Text from templates |
| `planning/demand_orders.json` | Orders with priority and daily chemical use | Own schema |
| `planning/parameters.json` | Transit times, STO lead times, transfer cost | Scenario assumptions |
| `history/exception_history_*.csv` | Past exceptions and their resolution time | 800 train + 200 holdout rows |
| `records/*.json` | Predictions, validations, approvals, executed STOs | Empty in the seed |

The mock S/4HANA uses the entity and field names of the API definitions SAP
publishes for `API_PURCHASEORDER_PROCESS_SRV`, `API_MATERIAL_STOCK_SRV`,
`API_PRODUCT_SRV`, and `API_BUSINESS_PARTNER`, limited to the fields CLEAR
uses. Code values: stock type `01` unrestricted and `06` in transit; order
type `NB` standard purchase order and `UB` stock transport order (SAP default
customizing, can differ per system); unit `TO` is the tonne. Dates are ISO
strings and quantities are JSON numbers, not the OData V2 wire format.
Shipments, documents, and demand orders have no counterpart in the core
S/4HANA APIs and use their own schema.

## Generator rules

### Scenarios (`src/clear_datagen/scenarios.py`)

Both scenarios concern plant 1100 (West Java, 0.5 days from Tanjung Priok).
Plant 1200 (East Java) can send stock transport orders with a lead time of
1 day at an assumed USD 45 per tonne.

| | S1, hero (SHP-1001) | S2, contrast (SHP-1002) |
|---|---|---|
| Material | CHEM-BX40, bleaching agent | CHEM-CX20, caustic agent |
| Purchase order | 4500001021, 600 t | 4500001022, 350 t |
| Plant 1100 stock / safety stock | 190 t / 150 t | 300 t / 100 t |
| Plant 1200 stock / safety stock | 300 t / 200 t | 140 t / 80 t |
| Plant 1100 use: all / critical + high / critical | 100 / 75 / 60 t per day | 50 / 39 / 30 t per day |
| Prepared events | Customs document hold, then an ETA slip with high berth congestion | Yard congestion |

S1 keeps the ratio of the original proposal: 1.9 days of coverage against a
resolution time of about 3 days.

### Documents (`src/clear_datagen/documents.py`)

Each shipment has an invoice, a packing list, a bill of lading, and a
certificate of analysis rendered from fixed templates. S1 carries exactly
one discrepancy: the packing list states 560 t (560 IBC totes, also on the
bill of lading), while the invoice and purchase order say 600 t. S2's
documents agree.

### Exception history (`src/clear_datagen/history.py`)

1,000 rows drawn with random seed 20261031. 20% are held out at random
(seed 20261032) to test prediction quality; the baseline uses only the
training rows.

| Column | How it is drawn |
|---|---|
| `exception_type` | document_discrepancy 35%, missing_document 20%, port_congestion 30%, customs_inspection 15% |
| `port` | Tanjung Priok 55%, Tanjung Perak 30%, Belawan 15% |
| `cargo_category` | bleaching_chemical 30%, caustic 30%, sizing_agent 20%, retention_aid 20% |
| `missing_documents` | 1 (75%) or 2 (25%) for missing_document, otherwise 0 |
| `has_document_discrepancy` | Always for document_discrepancy, 15% of missing_document, never otherwise |
| `congestion_level` | port_congestion: elevated 40%, high 60%. Others: normal 60%, elevated 25%, high 15%. October to December shifts both toward congestion |
| `forwarder` | FWD-A to FWD-E, uniform |
| `origin_country` | CN, DE, FI, JP, KR, US, uniform |
| `month` | 1 to 12, uniform |

`resolution_days` is the sum of these effects plus normal noise (standard
deviation 0.35 days), floored at 0.5 days and rounded to 0.1:

| Effect | Days |
|---|---|
| Base by type | document_discrepancy 2.5, missing_document 3.0, port_congestion 0.6, customs_inspection 1.8 |
| Port | Tanjung Priok +0.3, Tanjung Perak 0, Belawan -0.2 |
| Congestion | normal 0, elevated +0.5, high +1.0 |
| Cargo | bleaching_chemical +0.3, caustic +0.2, others 0 |
| Forwarder | FWD-A -0.2, FWD-C +0.4, others 0 |
| Each missing document after the first | +0.8 |
| Discrepancy on an exception of another type | +0.6 |

`origin_country` has no effect and `month` acts only through congestion:
both are distractors that a good model should not rank as drivers.

The Level 2 baseline predicts the median resolution time of training rows
with the same exception type, port, and congestion level. Groups with fewer
than 10 rows fall back to type and port, then to type alone.
